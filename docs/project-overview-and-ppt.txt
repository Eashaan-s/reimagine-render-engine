A1. What the project is

Reimagine Render Engine is a student capstone desktop application for Windows. It helps an architect or student preview a photorealistic image from an early drawing. The user does not build a 3D model or open a node-based AI tool. They stay in one window: drawing in the middle, instructions on the left, result on the right.

Scientifically this is image-to-image translation: one picture of a building (a wireframe or architectural render) is transformed into another picture (a photoreal preview), guided by a written instruction and an optional style photograph. The project does not train a new neural network. It packages a documented image-edit graph into a usable client.

The window title is Reimagine Render Engine only. Third-party lab branding was removed.

A2. Why it exists

Photoreal visualization is slow if every option needs CAD, materials, lighting, and a render farm. Early design still lives in 2D drawings. The gap is a fast “what if this drawing looked like that material and that light?” preview. The app is for concept discussion, not construction documents or BIM.

A3. What the user does (workflow anyone can follow)

1. Open the app. Three columns plus a status bar.
2. Drop or import the drawing into Input (PNG, JPG, WEBP). Filename and resolution appear underneath.
3. Optionally drop a style photo on the left (a real interior, a material board, a finished render).
4. Type a texture prompt (example: change image 1 to the materials and mood of image 2). Add style, tag, and lighting chips if useful.
5. Leave Simple mode, or open Advanced to set sampler, steps, CFG, and seed.
6. Click Generate. The app copies those fields into four fixed slots in a prepared graph and builds one job package.
7. At the current progress review (about 70 percent of the client): that job is complete and ready for a GPU inference worker. The worker is the remaining stage. When attached, a PNG appears in Output; Export saves it; History keeps recent previews.

A4. Progress delivered so far (what to claim tomorrow)

30 percent — UI shell (progress/30-ui-shell). Same layout. Import and preview work. Generate is blocked on purpose.
50 percent — Workflow mapping (progress/50-workflow-mapping). Generate fills the graph and can write mapped JSON. No GPU.
70 percent — Full client-side job. Desktop + secure bridge + mapping + export/history/status. Inference worker drawn as a black box. No vendor login in this review.
100 percent — Repository root is the full product (including a hosted GPU adapter). Not the focus of tomorrow if the supervisor asked to hide vendor config.

A5. System architecture (layers)

Think of four rooms in one house.

Room 1 — Renderer (the visible window)
Files: src/renderer/index.html, styles.css, renderer.js
This is an HTML page inside Electron. It cannot talk to the disk or a GPU by itself. It only draws the UI and remembers files in memory as data URLs.

Room 2 — Preload bridge (the locked door)
File: preload.js
Electron security: the page does not get Node.js. preload exposes a small API named window.reimagine. The page may call only those methods.

Room 3 — Main process (the operating-system process)
File: main.js
Creates the frameless window, min/max/close, save dialogs, and Generate handling. When Generate fires, main validates the base image, calls the workflow mapper, and (in the full product) sends the job to an inference client.

Room 4 — Workflow mapping (the form-filler)
File: src/services/workflowBuilder.js
Assets: workflows/workflow.json and workflow-api.json, plus scripts/convert-workflow.js
Loads a prepared ComfyUI API prompt and writes the user’s values into fixed node IDs. It does not invent a new graph.

Optional room — Inference worker (GPU image-edit)
In the full system this is a hosted GPU job that returns a PNG. Tomorrow: name it Inference worker only.

A6. Every UI component (left to right)

Title bar
Shows Reimagine Render Engine. Drag to move the window. Buttons: minimize, maximize, close. Functions: setupWindowControls, IPC window-control.

Left panel — Generate Style and Prompt
Texture Prompt: free text. Combined later with chips into one instruction.
Reference Image dropzone: optional style photo. setupDropzone, style-clear.
Style Preset chips: Exterior, Interior, Modern, and similar. createMultiSelect.
Tags: Building, Garden, Pool, and similar.
Lighting Style: Morning, Golden Hour, Overcast, and similar.
Generate button: handleGenerate.

Middle panel — Input
Large stage for the wireframe. Drop, click, or Import. Shows pixel size and file name. Clear button removes it.
Controls: Simple vs Advanced. Advanced: Sampler (Euler and others), Steps (default 4), Seed (empty means random), CFG Scale (default 1.0).

Right panel — Output
Placeholder until a result exists. Then the PNG, resolution, file name, render time.
Export: save-dialog PNG under Pictures / Reimagine Renders (export-image).
History strip: thumbnails of recent outputs; folder button opens the renders directory.

Status bar
Dot plus Idle / Mapping / Error and a short message. setStatus. During a live worker, progress messages can appear.

A7. Every software component and important functions

bootstrap
Starts the page: builds chip menus, dropzones, button listeners, first status message.

setupDropzone
Click, drop, or paste-style file pick. Converts the file to a data URL. Updates preview. Clear resets state.

fileToBase64
File object to data URL for IPC.

createMultiSelect
Multi-select dropdown that becomes chips (style, tags, lighting).

handleGenerate
Checks that a base image exists. Collects prompt, chips, sampler fields, both images. Calls window.reimagine.generateRender. On success shows the PNG and history. At 50 percent mapping-only, shows seed and saved JSON path instead of an image.

handleExport
Sends the current output to main for a Save dialog.

setStatus, startTimer, stopTimer, nextOutputName
Status text, elapsed time, sequential output names.

showOutput, addToHistory, renderHistory, selectHistoryItem
Output canvas and strip.

window.reimagine (preload)
generateRender -> trigger-generation
exportImage -> export-image
getConfig -> get-config
openRendersFolder -> open-renders-folder
windowControl -> window-control
onGenerationProgress -> generation-progress

main.js
createWindow: 1440 by 900, frameless, loads index.html with preload.
trigger-generation: requires base image; buildWorkflowPayload; in full product, client.generate.
export-image: writes PNG.
open-renders-folder: Pictures / Reimagine Renders.

workflowBuilder.js
loadBaseWorkflow: reads workflow-api.json.
assemblePrompt: lead sentence plus presets, tags, lighting, textarea.
buildWorkflowPayload: writes nodes 370, 371, 377, 368; returns workflow, seed, prompt.
randomSeed if the user left seed empty.
applyModelOverrides only if model filenames are set in the environment (not shown tomorrow).

convert-workflow.js
Turns a ComfyUI UI export into the compact API JSON. Keeps the graph that depends on node 370. Run when the graph file is updated, not every Generate.

Frozen node meanings (say these out loud)
370: this is the building drawing.
371: match this look (optional).
377: do this in words.
368: how many steps and how strongly to follow the prompt.

Job package shape (no secrets)
{
  "input": {
    "workflow": { "...filled API prompt..." },
    "images": [
      { "name": "reimagine_base.png", "image": "<base64>" },
      { "name": "reimagine_style.png", "image": "<base64>" }
    ]
  }
}

A8. Architecture in one paragraph

The renderer collects two images and a prompt. Preload is the only legal path into the operating-system process. Main asks workflowBuilder to stamp those values onto a frozen graph. The result is a job a GPU inference worker can run. At 70 percent that job is real; the worker connection is next. At 100 percent a cloud GPU adapter submits and polls until a PNG returns to Output.

A9. What is done vs not done (honest)

Done: branding, three-column UI, import, chips, advanced sampler fields, IPC, mapping, export, history, status, literature notes, 30/50 snapshots, architecture docs.
Next: attach the inference worker for a live photoreal demo (full product already exists in the repo root; this review may omit vendor details).
Not claimed: a new model, a new graph, BIM, or construction drawings.

A10. Literature in two sentences (if asked)

The problem is I2I (pix2pix). Control and instructions come from ControlNet and InstructPix2Pix. The deployed family is Qwen-Image plus Qwen2.5-VL. Architects also care about intent, not only photorealism (Yeh et al., arXiv:2303.11483). Tools are not papers.
